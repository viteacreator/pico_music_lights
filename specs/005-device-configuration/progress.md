## Correction milestone — firmware integration and storage safety

The following gaps from the initial matrix have now been addressed in the current branch, but the overall status remains **implementation in progress** until final review and verification complete:

- Normal firmware startup now constructs the RP2040 backend/store/service/diagnostics/runtime coordinator, independently inspects both slots, establishes persistent or explicit factory/no-record service state, and publishes the selected configuration before enabling rendering. `src/audio/audio_app.cpp`, `src/config/config_boot.cpp`, and `src/led/diagnostic_renderer.cpp` contain the integration; `startup_load_and_factory_fallback` covers the host-side boot decision and runtime adaptation.
- The current-board adapter publishes only channels 0–5, resolves GPIO from board configuration, overlays canonical calibration, and maps disabled retained counts to runtime zero. `src/config/runtime_adapter.cpp` and `disabled_channel_retained_count_runtime_zero` cover this boundary.
- Diagnostic-scene cycling is disabled by default; explicit effect-scene staging remains the development action that enables a chosen scene.
- Save preparation (validation, serialization, read-only inspection, target selection, and fixed activation planning) occurs before LED/audio safe points. Erase/program/commit begins only after both safe points and activation. Activation success is recorded independently from persisted success so precommit/unknown failures retain the old comparison baseline and dirty state.
- `DeviceConfigStore` owns a non-reentrant 12,544-byte fixed workspace instead of placing multiple 4,096-byte buffers on the stack. Measured host sizes are: `sizeof(DeviceConfiguration)=980`, `sizeof(EffectDeviceConfig)=106`, `sizeof(SlotInspection)=988`, `sizeof(LoadResult)=2968`, and `sizeof(DeviceConfigStore)=12568`. Payload serialization uses a 978-byte bounded automatic buffer; load/save result objects account for the remaining bounded automatic storage. No storage buffer is used from a real-time path.
- Fake flash now targets read/erase/data-program/commit operations by operation number, byte position, and address range, retains a bounded event trace, and supports interruption at every byte of the final page. The exhaustive commit-page test reboots after all 256 interruption positions; positions before byte 16 are invalid/uncommitted and positions 16–255 are valid because the remainder of the programmed page is intentionally `0xFF`.
- The RP2040 backend derives `application_end` from `__flash_binary_end`, rejects all access outside the two-slot region, validates SDK alignment, and uses SDK `flash_safe_execute`. This firmware is single-core and does not link `pico_multicore`; SDK flash-safe execution therefore disables current-core interrupts. If future code links `pico_multicore`, the SDK changes to multicore lockout and refuses unsafe execution unless the other core has initialized its lockout victim. This prevents accidental silent two-core XIP use.
- `src/storage/persistent_region_guard.ld` asserts at link time that `__flash_binary_end <= 0x101fe000`. `tools/test_persistent_link_guard.py` proves a valid end links and `0x101fe001` fails before artifact generation; the authoritative verifier runs this negative test in addition to its independent artifact check.
- Persisted runtime enums now pass through explicit schema-ID switch mappings in `src/config/schema_enum_mapping.cpp`; codec casts from runtime ordinals were removed.
- Bounded diagnostics and formatting now cover boot source, presence, both slots, selection/target/sequence ambiguity, validation, operation phase/status, commit uncertainty, dirty state, safe-point/flash timings and counters, and flash/image bounds.

Physical validation remains unperformed and must not be inferred from these software results.

## Independent review after correction milestone

The independent re-audit confirmed that startup loading, board-only runtime adaptation, audio pause/resume primitives, per-slot RP bounds, explicit enum mapping, the linker assertion, Off-record canonicalization, and telemetry hookup improved the implementation. Follow-up fixes removed the synchronous ready-block wait from audio safe-point acquisition, added retained-resource structural rollback/safe-disable behavior, and removed one redundant serialization buffer.

The review also identified remaining software work, so neither this document nor PR #3 marks software completion: full per-effect non-applicable-field canonicalization; one-to-one R005-067 tests and complete field-specific validation diagnostics; richer fallback/schema/timing diagnostics; cumulative fake-flash fault addressing and every prior/new-slot authority combination; a full intentionally oversized firmware negative build; exact worst-case stack analysis; and host fakes that exercise structural claim failure/rollback independently of Pico hardware. These are software gaps, not physical-validation items. The configuration service/coordinator APIs are integrated and constructed by firmware, but Feature 005 intentionally exposes no USB/network editor transport; later approved features are responsible for invoking editing operations. Physical validation remains owner-only.
